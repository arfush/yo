# AGENTS.md

Памятка для ИИ-агентов, которые работают с репозиторием **Yonime**. Прочитай её целиком перед первым изменением: здесь описаны архитектура, инварианты и правила, нарушение которых ломает приложение или релизный процесс.

## 1. Обязательное правило: Conventional Commits 1.0.0

**Все агенты обязаны оформлять коммиты по [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/).** Это требование репозитория, а не рекомендация.

Формат:

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

Правила:

- `type` — один из `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- В проекте дополнительно используется тип `release` — его требует GitHub Actions (см. раздел «Релизы»).
- `scope` опционален; используй имя пакета или подсистемы: `ui`, `playback`, `animelib`, `store`, `library`, `browser`, `kodik`, `updates`, `mpv`.
- Описание — краткое, в повелительном наклонении, со строчной буквы, без точки в конце. Ориентир — до 72 символов.
- Тело коммита объясняет **почему** изменение нужно, а не пересказывает diff. Переносы строк — по 72 символа.
- Несовместимое изменение: `feat(api)!: ...` и/или футер `BREAKING CHANGE: ...`.
- Один коммит — одно логическое изменение. Не смешивай рефакторинг, фичу и правку форматирования.
- Агент обязан сам коммитить завершённую работу и не оставлять изменения только в рабочем дереве. Исключение — коммиты `release:`: их создаёт только пользователь по отдельной просьбе.
- Не добавляй посторонние трейлеры, рекламные подписи и упоминания инструментов, если пользователь об этом не просил.
- Язык сообщений коммитов — английский.

Примеры:

```text
feat(playback): keep the mpv playlist ordered while preloading
fix(animelib): wait for the rate-limit window before retrying
docs: describe the Kodik fallback in AGENTS.md
refactor(store): extract history reordering into a transaction
release: v1.1
```

### Релизные коммиты

`release` — намеренно нестандартный тип, потому что workflow `.github/workflows/release.yml` запускается только при сообщении, начинающемся с `release:`. Формат первой строки:

```text
release: v1.2
```

Допускается и `release: 1.2` (workflow добавит `v`), но в этом репозитории принят вариант с `v`. Всё, что идёт после первой строки, публикуется как описание GitHub Release, поэтому тело релизного коммита должно быть готовым текстом заметок, а не служебными фразами.

Не переписывай историю и не делай force-push без явного указания пользователя.

## 2. Что это за проект

Yonime — десктопное Windows-приложение для ведения личной аниме-библиотеки и просмотра серий через AnimeLIB. Оно:

- принимает ссылку на тайтл AnimeLIB или его slug;
- показывает озвучки, серии и статус тайтла;
- запускает mpv с очередью серий, автопереходом, продолжением с места и главами;
- хранит историю, прогресс, обложки и настройки локально;
- при первом запуске сама устанавливает Chromium и mpv;
- обновляется из GitHub Releases.

Приложение неофициальное и никак не связано с AnimeLIB.

## 3. Технологический стек

- **Go 1.26.5**, модуль `github.com/arfush/yonime`.
- **Gio** (`gioui.org`) — весь интерфейс рисуется вручную, нативных виджетов нет.
- **SQLite** (`modernc.org/sqlite`) — локальная база.
- **Playwright Go + Chromium** — авторизация на сайте и резолв Kodik.
- **mpv** — воспроизведение (внешний процесс, управление по IPC).
- **7-Zip-распаковка** (`github.com/bodgit/sevenzip`) — установка mpv.
- **Win32 API** (`golang.org/x/sys/windows`) — трей, кастомное окно, DPI.
- `third_party/npipe` — локальный replace для named pipes на Windows.

Сборка идёт с `CGO_ENABLED=0` под `GOOS=windows`.

## 5. Поток данных

1. `ui.Run` создаёт окно и `application`.
2. `attachWindow` проверяет токен, при необходимости устанавливает Chromium, просит авторизацию, затем устанавливает mpv и показывает главный экран.
3. Ввод ссылки -> `mainWindow.startLoading` -> `library.Fetch` или `library.Load`.
4. `library` читает токен, вызывает `animelib.Client`, сохраняет метаданные в `store`, подтягивает обложку.
5. Страница тайтла вызывает `library.Save` (только по кнопке «Сохранить») и `startPlayback`.
6. `library.PlaybackPlan` строит список серий выбранной озвучки.
7. `playback.Service` резолвит текущую серию (AnimeLIB MP4, иначе Kodik HLS), запускает mpv и догружает соседние серии в фоне.
8. Прогресс сохраняется в `history`, главы — в `introdb_cache`.

## 6. Ключевые инварианты

### Данные

- Каталог данных: `%APPDATA%\yonime` (через `os.UserConfigDir`).
- Файлы: `yonime.sqlite`, `animelib_token.txt`, `browser/`, `covers/`, `mpv/`, `updates.json`, `update/`, `watchparty.json`.
- **Списки серий, озвучки и URL обложек не кэшируются в SQLite.** Они загружаются заново при каждом открытии страницы тайтла.
- Таблица `history` хранит только выбранную озвучку, серию, позицию и длительность.
- Проект первого релиза: миграций и совместимости со старыми базами нет. Схема создаётся с нуля; при будущих изменениях схемы миграции нужно добавлять явно.
- Токен нельзя писать в логи, базу, сообщения об ошибках или коммиты.

### AnimeLIB

- Базовый URL API — `https://api.cdnlibs.org`; заголовки должны имитировать сайт (`Referer`, `Origin`, `Site-Id`, `User-Agent`).
- Без токена защищённые запросы должны возвращать понятную пользователю ошибку на русском.
- Лимит AnimeLIB — около 100 запросов в фиксированное 60-секундное окно. Общий rate limiter в `animelib/rate_limit.go` обязателен: не обходи его, не запускай неограниченный параллелизм и не убирай ожидание после 429.
- Семафор клиента ограничивает одновременные запросы; новые тяжёлые запросы добавляй через существующий клиент.
- `ParseInput` должен принимать и полную ссылку, и slug, и ссылки зеркал.

### Playback

- Одновременно может работать только одна сессия mpv.
- Текущая серия резолвится **до** запуска окна mpv; ошибка должна оставить пользователя в приложении.
- Очередь пополняется окнами: вперёд до 30 серий, назад до 5. Не резолвь весь тайтл сразу.
- AnimeLIB-плеер имеет приоритет; Kodik — только фолбэк для серий, которых нет в прямом плеере.
- `playlist-pos` в mpv может прийти после `file-loaded`; не привязывай прогресс к событиям без проверки фактической позиции.
- Прогресс сохраняется не чаще раза в 5 секунд, при паузе и при завершении. Позиция < 5 секунд и позиция near-end сбрасываются.
- Главы introdb кэшируются, включая отрицательный результат (`no_data`).
- Не блокируй event loop сессии длительными резолвами: используй горутины и существующие мьютексы.

### Совместный просмотр

- По сети ходит только якорь (`State` с позицией и часами хоста), а не поток позиций. Гость экстраполирует позицию сам, поэтому потерянный пакет не рассинхронизирует комнату.
- Провайдеры равноправны: Cloudflare DO и Supabase Realtime используют один и тот же JSON поверх WebSocket (`internal/watchparty`). Новый провайдер добавляется в `transport.go`, `config.go` и `state.go`, без правок UI.
- Хост публикует якорь раз в 4 секунды при воспроизведении и раз в 10 секунд на паузе, плюс сразу после паузы, смены серии и перемотки. Не поднимай частоту: от неё напрямую зависит расход квоты Supabase.
- Смещение часов считается по входящим якорям (минимум `local_recv - anchor_host` по окну из 96 сэмплов). Не заменяй это на ping/pong — это лишний трафик.
- Рассинхрон до ~900 мс правится скоростью (`0.94–1.06`), больше — точным seek. Не убирай `--hr-seek=yes`: без него seek округляется до ключевого кадра.
- Управлять воспроизведением может только создатель комнаты. Гость повторяет состояние, но не публикует своё.
- Хост публикует якорь сразу после подключения, даже пустой: для гостя это доказательство, что комната существует. Не убирай этот «hello-ответ» — иначе гость решит, что ключ неверный.
- Реле живут на бесплатных тарифах: не добавляй периодических сообщений сверх перечисленных и не дублируй доставку.
- Эндпоинты берутся из `%APPDATA%\yonime\watchparty.json` или из ldflags (`watchparty.CloudflareURL`, `watchparty.SupabaseURL`, `watchparty.SupabaseKey`). Пустая конфигурация должна давать понятную ошибку, а не панику.

### Kodik

- Kodik `/ftor` требует браузерную сессию. Резолв идёт через headless Chromium, а не через прямой HTTP-запрос.
- Один headless-браузер живёт на сессию; резолвы сериализованы, кэш ссылок — 45 минут.
- Не заменяй Playwright на `net/http` и не пытайся обойти защиту иначе: это уже проверено и не работает.

### Браузер и авторизация

- Пользователь входит на сайте AnimeLIB сам; приложение только открывает сайт и читает сохранённый токен.
- Профиль Chromium persistent, чтобы сессия переживала перезапуск.
- Токен считается истёкшим за 2 минуты до фактического окончания (`token.ExpiryMargin`).
- `Manager.Close` должен уметь прервать и установку, и авторизацию.

### Обновления

- Источник — последний GitHub Release репозитория `arfush/yonime` (переопределяется ldflags).
- Обязательна проверка SHA-256; не ослабляй проверки URL, размера и сигнатуры файла.
- Windows блокирует запущенный exe, поэтому замена идёт через `updater` и скрытый `cmd.exe`-хелпер.
- Не удаляй `CheckTarget`, проверку `MZ`-заголовка и очистку временных файлов.

### UI

- Gio — immediate mode. Не храни указатели на виджеты между кадрами и не мутируй список истории во время `List.Layout`.
- Никаких блокирующих вызовов в `layout`: сеть, диск и mpv — только из горутин.
- Фоновые результаты передаются в UI через каналы и `w.Invalidate()`.
- Когда окно скрыто в трее или уступает экран mpv, анимации должны переставать запрашивать кадры.
- Пользовательские строки — на русском. Комментарии и внутренние ошибки — на английском; ошибки, которые видит пользователь, — на русском.
- Кастомный заголовок и трей реализованы через Win32; не заменяй их стандартным окном без причины.
- Закрытие окна сворачивает приложение в трей. Полностью закрывает только пункт меню трея.

### Платформы

- Windows — основная и единственная реально поддерживаемая платформа.
- Файлы с Win32-кодом имеют build tag `//go:build windows`; для остальных ОС должны оставаться заглушки, чтобы пакет компилировался.
- Не меняй `third_party/npipe` без необходимости: это локальный replace для named pipes.

## 7. Команды

Все команды выполняются из корня репозитория.

```powershell
# Полная проверка
go test ./...
go vet ./...
gofmt -l .\cmd .\internal .\ui

# Один тест
go test ./internal/playback -run TestName -v

# Сборка (Windows GUI, без консоли)
.\build.ps1 -Version 1.0 -Arch amd64

# Или через make
mingw32-make build VERSION=1.0 ARCH=amd64
mingw32-make check
```

`build.ps1` выставляет `CGO_ENABLED=0`, `GOOS=windows` и передаёт версию/репозиторий через ldflags. Без `-Version` версия берётся из `internal/version/version.go`.

Интеграционный тест авторизации запускает настоящий Chromium и по умолчанию пропускается:

```powershell
$env:YONIME_AUTH_TEST = "1"
go test ./internal/browser -run TestAuthorizeIntegration -v
Remove-Item Env:\YONIME_AUTH_TEST
```

## 8. Правила разработки

- Соблюдай `gofmt`; код должен проходить `go vet`.
- Следуй стилю окружающего кода: небольшие функции, ранние возвраты, комментарии по делу.
- Новые зависимости добавляй только при явной необходимости и объясняй это в PR/коммите.
- Ошибки оборачивай через `%w` и добавляй контекст.
- Для новых неочевидных решений добавляй короткий комментарий, объясняющий причину.
- Тесты не должны ходить в сеть, запускать Chromium/mpv или зависеть от реального `%APPDATA%`. Используй `t.TempDir()`, `httptest` и внедряемые зависимости.
- Покрывай тестами чистую логику: парсинг, выбор серии/озвучки, прогресс, rate limit, обновления, UI-хелперы.
- Не коммить `yonime.exe`, `dist/`, базы, токены, `updates.json`, `.idea/` и прочие локальные артефакты.
- Перед коммитом проверь `git status` и `git diff`: в индекс не должны попасть секреты и случайные файлы.

## 9. Передача работы в основной проект

Агент работает в отдельном worktree с detached HEAD: его коммиты не видны в
основном чекауте, пока их туда не переложат. Основной проект — единственный
источник истины для пользователя: в нём он запускает `go test`, собирает exe и
делает релиз. Задача не считается выполненной, пока коммит не оказался в `main`
основного чекаута.

Основной чекаут в этом окружении — `C:\Users\Nazar Bykasov\projects\yonime`
(ветка `main`). Точный путь всегда можно получить через `git worktree list`:
это единственная запись с веткой `main`, остальные — worktree агентов с
detached HEAD.

### Порядок действий

1. Проверить, что основной чекаут чист и не ушёл вперёд:
   ```powershell
   git -C "<main>" status --short --branch
   git -C "<main>" log --oneline -1
   ```
2. Перебазировать свою работу на верхушку `main`. Перебазируется ветка агента,
   а не `main`:
   ```powershell
   git rebase <main-tip>
   ```
3. Повторить проверки после rebase: новые коммиты в `main` могли задеть те же
   файлы. `go build ./...`, `go vet ./...`, `go test ./...`.
4. Перемотать `main` только fast-forward-ом:
   ```powershell
   git -C "<main>" merge --ff-only <sha>
   ```
5. Убедиться, что коммит на месте и дерево чистое:
   ```powershell
   git -C "<main>" log --oneline -1
   git -C "<main>" status --short
   ```
6. Написать пользователю SHA и первую строку коммита, на который теперь
   указывает `main`.

### Жёсткие правила

- Только `--ff-only`. `merge` без fast-forward, `reset --hard`, `rebase` и
  `cherry-pick` прямо в основном чекауте запрещены: там может лежать
  незакоммиченная работа пользователя.
- **Не делать `git push`** и не трогать `origin` без явной просьбы. Локальный
  `main` вправе опережать `origin/main`.
- Если основной чекаут грязный — остановиться и перечислить мешающие файлы. Не
  прятать правки через `stash` и не откатывать их.
- Если fast-forward невозможен, перебазировать свою работу на актуальный `main`
  и повторить шаги. Мержить свою ветку в `main` с созданием merge-коммита
  нельзя.
- Конфликты разрешаются только в worktree агента. Если конфликт затрагивает
  чужую незавершённую работу или уверенности нет — остановиться и спросить.
- Коммиты `release:` по-прежнему создаёт только пользователь.
- Worktree после передачи оставлять как есть: он нужен для следующих правок.

## 10. Релизы

Релиз полностью автоматизирован:

1. Изменения попадают в `main`.
2. Коммит с первой строкой `release: vX.Y` запускает workflow.
3. Workflow прогоняет тесты, собирает `amd64`, `arm64`, `386`, считает SHA-256 и публикует GitHub Release.
4. Тело релизного коммита становится описанием релиза; если оно пустое, GitHub генерирует заметки сам.

Не создавай теги и релизы вручную в обход workflow. Не меняй формат `release:` без обновления парсера в `.github/workflows/release.yml`.

## 11. Известные ловушки

- **Запущенный exe нельзя перезаписать** — только через `updater` после выхода процесса.
- **Win32-трей живёт в отдельном message loop.** Вызовы `ShowWindow` из UI-потока могут заблокировать оба потока; скрытие уже вынесено в горутину.
- **`playlist-pos` приходит с задержкой.** Для прогресса и resume используй фактическую позицию, а не только событие.
- **Gio List нельзя мутировать во время layout.** Удаление строк обрабатывается после раскладки.
- **Скрытое окно не должно крутить анимации** — иначе процесс ест CPU в трее.
- **AnimeLIB отвечает 429 без полезного `Retry-After`.** Опирайся на локально отслеживаемое окно.
- **Kodik без браузера не резолвится.** Не «оптимизируй» это в HTTP-клиент.
- **Сборка только с `CGO_ENABLED=0`.** Не добавляй зависимости, требующие cgo.

## 12. Definition of Done

Перед завершением задачи:

- [ ] `gofmt` не находит изменений;
- [ ] `go vet ./...` проходит;
- [ ] `go test ./...` проходит;
- [ ] затронутая логика покрыта тестами или объяснено, почему нет;
- [ ] проверен ручной сценарий на Windows, если менялся UI, mpv, трей или установка;
- [ ] в диффе нет секретов, баз, бинарников и локальных файлов;
- [ ] коммит оформлен по Conventional Commits 1.0.0;
- [ ] работа перебазирована на актуальный `main` и `main` основного чекаута перемотан на неё через `merge --ff-only` (раздел 9);
- [ ] для релиза — первая строка `release: vX.Y` и готовые заметки в теле.
